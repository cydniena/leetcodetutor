LeetCode Tutor

A study tracker for coding-interview prep, built around a single question: am I actually getting better? Deliberately not an AI tutor, not a code judge, and not a LeetCode scraper.

This page is static. The app is an Express API with a Postgres database and session cookies, so it cannot run on GitHub Pages — there is no server here and nothing to log in to. The charts below are real output from the six analytics queries, run against the seeded demo history that ships with the repo (server/scripts/seed.js). They are not one person's real study record. To use it for real, clone the repo and run it locally.

Why this exists

Every feature in the app has to trace back to one of these four points. If a feature serves none of them, it doesn't get built.

Clarity — what is the problem?

People prepare in a scattered way: they pick problems at random, solve the ones they already recognise, and keep no record of what they attempted or why an attempt failed. Faced with an unfamiliar medium, they can't tell which technique applies — because they learned problems as one-offs rather than as members of a pattern.

Consequence — what does it cost?

Weeks of study with nothing measurable to show, and failed interviews the person can't diagnose. Concretely: hours re-solving things already known while the real weak spots go untouched, and no way to answer “am I better than I was last month?”

Cause — why does it happen?

  • No record of attempts, so no feedback loop exists
  • No organisation by pattern, so recognition never develops
  • No sequencing — problems attempted before their prerequisites are solid
  • No review, so solved material decays and gets re-learned

Confirmation — how would we know it helped?

Log 15 attempts by hand first. That's the baseline. The app works if time-to-solve falls, the share of solves needing a hint falls, and repeat attempts on old problems hold up instead of degrading. If those three numbers don't move, the app failed — and the schema exists to make them computable.

The three numbers

Hand-logged baseline attempts versus everything logged since. This is the comparison the whole project is judged on.

What the analytics actually show

Six queries over the app's own tables — no warehouse, no event pipeline. Each chart here is the unmodified result of one of them.

Time-to-solve, by difficulty, by week

Average minutes on solved attempts. Give-ups are excluded — they'd measure persistence, not speed.

Hint dependency: share of solves needing hint level 2 or deeper

Hints are a ladder of three, authored by hand per pattern. Needing the deep ones means the pattern hasn't landed yet. A database constraint keeps this honest: a “clean” solve cannot carry a hint, and a hinted solve must carry at least one.

Retention: how repeat attempts hold up as the gap grows

Clean-solve rate on second-and-later attempts at the same problem, bucketed by days since the previous attempt. Both the gap and the previous outcome come from a window function over attempt — no extra column needed.

Mastery grid

Per pattern: attempts, clean-solve rate, last attempted. Patterns with zero attempts still appear — those rows are the untouched weak spots, which is the entire point. The grid counts attempt_pattern, the pattern you say you actually used, not the problem's tags — so it measures technique practised rather than technique intended.

Today, and plan adherence

What to do today

Overdue plan items plus reviews that have come due. Day boundaries use the user's own timezone, never the server's.

    Plan adherence

    Of the items whose target date has passed, how many were finished on time rather than late or skipped.

    The schema

    Sixteen tables. Reference data is seeded and admin-editable; everything else belongs to a user and is scoped by user_id in the data layer.

    Reference — read-only for learners

    • topic — with a self-referencing prerequisite relation
    • pattern — finer-grained than topic; carries the explainer
    • pattern_hint — the graduated ladder, levels 1–3
    • problem — title, difficulty, URL. Metadata and a link only, never the problem text
    • problem_pattern — many-to-many, with one primary pattern

    User-owned — the CRUD surface

    • attempt — minutes, outcome, hint level, confidence, reflection
    • attempt_pattern — the pattern you actually used
    • plan / plan_item — reorderable, reschedulable
    • goal / goal_topic — target date, hours, focus topics
    • review — spaced repetition on a fixed 1 / 3 / 7 / 21 ladder
    • note — attached to a problem or a pattern, never both

    Three constraints doing real work

    • attempt_hint_matches_outcome — a clean solve must have hint level 0, a hinted solve at least 1. Keeps the hint-dependency metric from drifting at the database level rather than by convention.
    • note_exactly_one_parent — (problem_id is not null) <> (pattern_id is not null). One table for notes, not two, without allowing an orphan or a note attached to both.
    • plan_item_completed_at_matches_status — (status = 'done') = (completed_at is not null). Makes “done on time” answerable, since a completion can't exist without its date.

    Decisions worth explaining

    Authorization lives in the data layer

    There is deliberately no findPlan(id). Every repository function for user-owned data takes the owner's id and puts it in the WHERE clause, so a missing row and a row you don't own are indistinguishable — both return 404, and the API never reveals which ids exist. The React route guards are convenience only.

    Session cookie, not a JWT in local storage

    HttpOnly, so no JavaScript can read the token, and SameSite=Lax. Sessions live in Postgres, which keeps Postgres the only datastore — no Redis to run.

    Raw SQL, no ORM

    The interesting parts of this project are the joins and the window function behind the retention metric. An ORM would hide exactly those. The cost is hand-written row mapping, paid willingly.

    One place decides what “today” is

    Day boundaries are a per-user question, so app_user.timezone drives them and nothing in the codebase may call current_date. Every “is this due?” routes through a single module.

    Attempts tag the pattern you used

    Prefilled from the problem's tags, then corrected by hand. It costs one extra table and one click per log, and it buys a mastery grid that notices when you solved a two-pointer problem with a hash map.

    Explicitly out of scope

    No LLM calls, no generated hints, no sandboxed code execution, no scraping. Hints and explainers are content authored by hand and stored as rows; the app stores, schedules and reveals them in order — nothing cleverer.

    Build status

    Built in vertical slices — migration, then data layer, then routes, then UI, then seed — so there is something runnable at the end of each.

    • 0 Skeleton, Docker Postgres, migration runner, catalog and seed done
    • 1 Auth — register, login, logout, password change, roles, ownership tests done
    • 2 Catalog reads, problem browser, progressive hint reveal, notes CRUD next
    • 3 Attempts CRUD, logging form, history to do
    • 4 Plans and plan items — reorder, reschedule to do
    • 5 Goals, reviews, today's queue, dashboard to do
    • 6 Analytics pages to do
    • 7 Admin catalog CRUD to do
    • 8 Account recovery — password reset by email, account deletion to do

    The analytics queries themselves already exist and are what this page renders — phase 6 adds the routes and the in-app charts on top of them, rather than rewriting the SQL.

    Running it

    Requires Node 20+ and Docker.

    git clone https://github.com/cydniena/leetcodetutor
cd leetcodetutor
npm run install:all
cp .env.example .env
npm run db:up        # Postgres 16 in Docker, host port 5433
npm run migrate      # apply migrations/*.sql in order
npm run seed         # catalog + 2 users + 12 weeks of demo history
npm run dev:server   # API on :4000
npm run dev:client   # UI  on :5173

    Seeded logins, both with password password123: learner@example.com (has the demo history) and admin@example.com (for catalog editing).
